2024 年的春天，在准备几场大厂面试的过程中，我发现即便是有几年经验的开发者，在谈到 MySQL 锁和 Redis 一致性这两个话题时，往往也只能背出几个名词。

但面试官最喜欢问的其实是那些“边界场景”：比如为什么有了隔离级别还要有间隙锁？为什么先删缓存再改数据库还是会有脏数据？

为了彻底搞懂这些，我花了半个月的时间翻阅了 InnoDB 的源码文档，并做了一系列压测实验。今天这篇博客，是对这段“闭关修炼”的硬核复盘。

## 第一部分：MySQL InnoDB 锁机制 —— 并不只是行锁那么简单

很多人认为 InnoDB 的行锁就是锁住那一行记录。实际上，**InnoDB 的锁是加在索引上的**。理解了这一点，你才能理解为什么有时候没命中索引会锁全表。

### 1. 三种行锁算法的物理差异
InnoDB 实际上有三种行锁的算法实现：

1. **Record Lock（记录锁）**：直接锁定索引记录。
2. **Gap Lock（间隙锁）**：锁定索引记录之间的间隙，不包括记录本身。它的唯一目的是：**防止幻读（Phantom Read）**。
3. **Next-Key Lock**：Record Lock + Gap Lock 的组合，锁定一个范围，并且锁定记录本身。

### 2. 为什么需要间隙锁？（解决幻读的底层逻辑）
在 `REPEATABLE READ`（可重复读）隔离级别下，如果没有间隙锁，会出现以下诡异情况：
- 事务 A 查询 `id > 10` 的记录，发现有 2 条。
- 事务 B 插入一条 `id = 15` 的记录。
- 事务 A 再次查询，发现变成了 3 条。这就是幻读。

**底层原理**：间隙锁在索引的空隙中插了一把“禁止掉入”的红旗。当事务 B 尝试在事务 A 锁定的间隙中插入新记录时，会被阻塞。正是由于间隙锁的存在，MySQL 的 RR 级别在很大程度上解决了幻读问题。

### 3. MVCC 与锁的协同：快照读 vs 当前读
这是最基础也最容易被忽略的点。
- **快照读（Snapshot Read）**：简单的 `SELECT`。它不加锁，底层利用 MVCC（多版本并发控制）读取 ReadView。
- **当前读（Current Read）**：`SELECT ... FOR UPDATE` 或 `UPDATE/DELETE`。它必须读取最新的记录，并给记录加锁。

**深度思考**：面试中常问的所谓的“不可重复读”，在快照读下靠 MVCC 解决，在当前读下靠锁解决。这种双轨制的设计，是 MySQL 在并发与一致性之间取得平衡的精髓。

## 第二部分：Redis 与 MySQL 的一致性 —— 现实世界的博弈

在分布式环境下，数据库和缓存是两个独立的系统，没有原生支持的分布式事务。我们只能通过一系列策略来“逼近”一致性。

### 1. Cache Aside Pattern 的经典争议：先删缓存还是后删？

#### 方案一：先删缓存，后改数据库
**致命伤**：高并发下的 Race Condition。
1. 线程 A 删缓存。
2. 线程 B 读缓存发现为空，去读数据库（旧值），并准备写回缓存。
3. 线程 A 修改数据库（新值）。
4. 线程 B 将旧值写回缓存。
**结果**：缓存里永远是脏数据。

#### 方案二：先改数据库，后删缓存（主流推荐）
**潜在风险**：如果在步骤 2 删缓存失败了怎么办？或者在高并发极小概率下，缓存失效瞬间发生并发读写，依然会有极短时间的脏数据。

### 2. 底层抗风险方案：延迟双删与 Canal 订阅

为了解决上述问题，我们有了更硬核的做法：

- **延迟双删**：在修改数据库后，先删一次缓存，睡眠几百毫秒后再删一次。
    - **逻辑内核**：第二次删除是为了确保在修改期间，由于并发读取而产生的可能脏数据被清除掉。但“睡眠多久”是个玄学，难以精确把控。
- **Canal 订阅 Binlog**：这是 2024 年大厂最通用的方案。
    - **底层原理**：将自己伪装成 MySQL 的从库，监听 Binlog 变更。一旦有数据更新，异步通知消费者去刷新缓存。
    - **优势**：解耦。业务流程只管写数据库，缓存刷新交给专门的组件，不仅可靠性高，还能自动重试。

### 3. Redis 自身的强一致性可能吗？

别忘了 Redis 自己的同步也是异步的（主从复制）。如果你要求绝对的强一致性：
1. **Redlock 算法**：尝试在多数派节点上加锁。但分布式时钟偏移和 GC 停顿会让 Redlock 在理论上依然存在失效可能。
2. **读写分离的坑**：主库刚写完，从库还没同步，这时候读从库就会读到旧值。

**复盘总结**：在架构设计中，**“最终一致性”是现实，“强一致性”是昂贵的理想**。大多数场景下，我们通过“过期时间强制兜底 + Binlog 异步补偿”就能覆盖 99.9% 的业务需求。

## 第三部分：写在最后

这次复盘让我明白，不管是 MySQL 的间隙锁，还是 Redis 的双删策略，它们本质上都在对抗一个物理事实：**在不确定的时间序列里，如何通过逻辑规则确定一个唯一的真理。**

面试官问这些，考察的不只是你的记忆力，而是你对“并发边界”的敬畏心。只有当你在脑海中能模拟出多个线程交织运行的路径，并能预见到哪里可能抛出异常、哪里可能产生脏数据时，你才算真正掌握了这些技术。
