## 一、Linux & 运维基础

### Q1：Linux 内核参数调优 — vm.swappiness

**面试官问法：**

> 你提到对 Linux 内核参数进行了调优，具体调整了哪些参数？为什么调整 `vm.swappiness` 能提升高并发性能？

**答题框架：**

```
问题现象 → 排查过程 → 参数含义 → 调整结果 → 量化验证
```

**核心知识点：**

- `vm.swappiness`：取值 0~100，值越低越倾向使用物理内存而非 swap
    - 默认值 60，高并发场景建议调到 10~20
    - 频繁 swap 导致 I/O 飙升、延迟增大
- 常用排查工具：`top` / `vmstat` / `iostat` / `free -h`
- 量化方式：用 `wrk` / `ab` 压测接口，对比调优前后 QPS 和 P99 延迟

**其他常见调优参数：**

|参数|作用|典型值|
|---|---|---|
|`net.core.somaxconn`|TCP 全连接队列长度|65535|
|`net.ipv4.tcp_max_syn_backlog`|半连接队列长度|65535|
|`fs.file-max`|系统最大文件描述符|1000000|
|`net.ipv4.tcp_tw_reuse`|允许复用 TIME_WAIT 连接|1|
|`vm.swappiness`|内存与 swap 使用倾向|10|

### Q2：CPU 使用率飙升排查 + 定位 Java 线程

**面试官问法：**

> 线上 CentOS 服务器 CPU 使用率突然飙升到 95%，你的排查流程是什么？如果是某个 Java 进程的某个线程在占用，如何定位到具体代码行？

**标准排查路径（必须流畅背下来）：**

```bash
# 第一步：找高 CPU 进程
top                          # 按 P 排序，找到高 CPU 的 PID，假设为 12345

# 第二步：找该进程内高 CPU 线程
top -H -p 12345              # 找到高 CPU 的线程 TID，假设为 12398

# 第三步：TID 转十六进制
printf "%x\n" 12398          # 输出：306e

# 第四步：在 jstack 输出中搜索该线程
jstack 12345 | grep -A 30 "306e"

# 第五步：读取栈帧，定位业务代码行
# 输出中 "at com.example.Service.doWork(Service.java:88)" 即为问题代码
```

**常见高 CPU 原因：**

- 死循环（最常见）
- 频繁 Full GC（JVM 堆不足）
- 正则表达式回溯
- 大量线程上下文切换

### Q3：Shell 脚本并发检测 100 台服务器

**面试官问法：**

> 你写过 Shell 脚本做自动化巡检，如果脚本需要并发检测 100 台服务器，你会怎么实现？

**方案一：后台并发 + wait（简单场景）**

```bash
#!/bin/bash
HOSTS=("10.0.0.1" "10.0.0.2" "10.0.0.3")  # ...100台
RESULT_DIR="/tmp/check_results"
mkdir -p "$RESULT_DIR"

check_host() {
    local host=$1
    # 执行检查，结果写入独立文件（避免并发写冲突）
    ssh "$host" "uptime && df -h && free -m" > "$RESULT_DIR/$host.txt" 2>&1
}

for host in "${HOSTS[@]}"; do
    check_host "$host" &
done
wait  # 等待所有后台任务完成

# 汇总结果
cat "$RESULT_DIR"/*.txt
```

**方案二：xargs 控制并发数（推荐）**

```bash
echo "${HOSTS[@]}" | tr ' ' '\n' | xargs -P 20 -I{} ssh {} "uptime"
# -P 20：最多 20 个并发，避免网络拥塞
```

**注意事项：**

- 控制并发数（通常 10~30），过多会导致网络拥塞和 SSH 连接数超限
- 结果写入独立文件，汇总时再合并，避免并发写同一文件的竞态问题

### Q4：MySQL 主从复制延迟排查 + MHA 原理

**面试官问法：**

> MySQL 主从复制延迟突然增大，你如何排查？MHA 自动切换的原理是什么，切换过程中如何保证数据不丢失？

**延迟排查步骤：**

```sql
-- 在从库执行
SHOW SLAVE STATUS\G

-- 关键字段：
-- Seconds_Behind_Master：当前延迟秒数
-- Relay_Log_Space：relay log 积压大小
-- Slave_SQL_Running_State：SQL 线程当前状态
```

**常见原因及处理：**

|原因|表现|处理|
|---|---|---|
|大事务|单条 SQL 执行时间长|拆分大事务|
|从库 I/O 瓶颈|relay log 积压|升级磁盘，开启并行复制|
|网络抖动|`Master_Log_File` 位点长时间不变|检查网络，重启 IO 线程|
|从库规格低|CPU/内存不足|升配，开启 `slave_parallel_workers`|

**MHA 自动切换流程：**

```
1. 主库宕机，MHA Manager 检测到心跳超时
2. 对比所有从库的 binlog 位点，找到数据最新的从库
3. 用最新从库补全其他从库缺失的 binlog（差异同步）
4. 将最新从库提升为新主库
5. 其他从库指向新主库，VIP 漂移到新主库
```

**数据安全保障：**

- 半同步复制（`rpl_semi_sync_master_enabled`）：主库等至少一个从库确认后再提交
- MHA 的 binlog 位点对比确保无数据丢失（RPO ≈ 0）

## 二、容器与 Kubernetes

### Q5：Pod 一直 Pending — 排查步骤

**面试官问法：**

> K8s 中一个 Pod 一直处于 Pending 状态，你的排查步骤是什么？

**第一步：看 Events**

```bash
kubectl describe pod <pod-name> -n <namespace>
# 重点看最底部的 Events 字段
```

**至少 5 种常见原因：**

|原因|Events 关键词|解决方法|
|---|---|---|
|节点资源不足|`Insufficient cpu/memory`|扩容节点或降低 request|
|节点有 Taint 未容忍|`node(s) had taint`|添加 Toleration 或清除 Taint|
|PVC 未绑定|`pod has unbound PVC`|检查 StorageClass 和 PV|
|镜像拉取失败|`ErrImagePull`|检查镜像名和 imagePullSecret|
|亲和性规则冲突|`0/N nodes are available`|检查 nodeAffinity/podAffinity|
|节点 NotReady|`node(s) were unschedulable`|检查节点状态|
|调度器异常|无 Events|`kubectl get pods -n kube-system` 查看调度器|

### Q6：Minikube vs 生产 K8s 差异

**面试官问法：**

> 你项目中用 Minikube，和生产 K8s 有哪些差异？迁移到生产要关注哪些问题？

**核心差异对比：**

|维度|Minikube|生产集群|
|---|---|---|
|Master 节点|单节点（无 HA）|3+ 节点 etcd 集群|
|网络插件|内置简单网络|Calico / Flannel / Cilium|
|持久化存储|hostPath（本地）|Ceph / NFS / 云盘|
|节点扩缩|手动|Cluster Autoscaler|
|镜像仓库|本地|私有 Harbor / 云镜像仓库|
|RBAC|宽松|严格最小权限|

**迁移生产重点关注：**

1. 网络策略（NetworkPolicy）：隔离 namespace 间流量
2. 资源配额（ResourceQuota + LimitRange）：防止单个应用耗尽集群资源
3. 镜像安全扫描：接入 Trivy 等工具
4. 日志和监控：确保 DaemonSet 方式部署采集器

### Q7：Docker 镜像优化

**面试官问法：**

> Docker 镜像构建时如何优化大小和构建速度？多阶段构建的使用场景是什么？

**大小优化：**

```dockerfile
# 1. 用 Alpine 基础镜像（~5MB vs Ubuntu ~70MB）
FROM openjdk:17-alpine

# 2. 合并 RUN 层，减少镜像层数
RUN apk add --no-cache curl wget && \
    rm -rf /var/cache/apk/*

# 3. 多阶段构建（核心技巧）
FROM maven:3.9-openjdk-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline        # 先只拷贝 pom，利用缓存
COPY src ./src
RUN mvn package -DskipTests

FROM openjdk:17-alpine AS runtime    # 只复制编译产物
COPY --from=builder /app/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
# 结果：镜像从 ~600MB 降至 ~150MB
```

**构建速度优化：**

- 变化少的层（系统依赖）放前面，变化频繁的层（业务代码）放后面，最大化利用构建缓存
- 用 `.dockerignore` 排除 `target/`、`.git/`、`node_modules/` 等

### Q8：K8s Service 类型 & Ingress

**面试官问法：**

> K8s 的 Service 有几种类型？Ingress 和 Service 的区别是什么？

**Service 四种类型：**

|类型|访问范围|使用场景|
|---|---|---|
|`ClusterIP`|仅集群内部|服务间调用（默认）|
|`NodePort`|集群外，通过节点 IP:Port|测试环境对外暴露|
|`LoadBalancer`|集群外，云厂商 LB|生产对外暴露（需云环境）|
|`ExternalName`|映射外部 DNS|访问集群外部服务|

**Ingress vs Service：**

```
Service（L4）：基于 IP + Port 的负载均衡，不理解 HTTP
Ingress（L7）：基于域名 / URL 路径的 HTTP 路由规则

Ingress 需要配套 Ingress Controller（如 nginx-ingress）才能工作
```

**典型 Ingress 配置：**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /user
        pathType: Prefix
        backend:
          service:
            name: user-service
            port:
              number: 8080
      - path: /order
        pathType: Prefix
        backend:
          service:
            name: order-service
            port:
              number: 8080
```

**各阶段耗时分配（参考）：**

```
健康检查通过      ~30s   readinessProbe 探测
────────────────────────
总计              ~4.5min
```

**K8s 滚动更新配置：**

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 最多多启动 1 个新 Pod
      maxUnavailable: 0  # 始终保证全量可用 Pod
```

**回滚命令：**

```bash
# 查看历史版本
kubectl rollout history deployment/my-app

# 回滚到上一版本
kubectl rollout undo deployment/my-app

# 回滚到指定版本
kubectl rollout undo deployment/my-app --to-revision=3

# 查看回滚状态
kubectl rollout status deployment/my-app
```

### Q10：Prometheus 架构 & 告警风暴治理

**面试官问法：**

> Prometheus 是 pull 还是 push 模型？如何避免告警风暴？

**Prometheus pull 模型：**

```
Prometheus 主动定时拉取（scrape）各 Exporter 暴露的 /metrics 接口
优点：服务发现简单，目标管理集中，易于调试
缺点：短生命周期 Job 可能被漏采（用 Pushgateway 补充）
```

**告警风暴治理（Alertmanager）：**

```yaml
# alertmanager.yml 核心配置
route:
  group_by: ['alertname', 'cluster']   # 同类告警合并为一条
  group_wait: 30s                       # 等待 30s 聚合同组告警
  group_interval: 5m                    # 同组告警 5 分钟内只发一次
  repeat_interval: 4h                   # 已发告警 4 小时后才重复

inhibit_rules:
  # 节点宕机时，抑制其上所有 Pod 的告警
  - source_match:
      alertname: 'NodeDown'
    target_match_re:
      alertname: 'Pod.*'
    equal: ['node']
```

**四种治理手段：**

1. `group_by`：合并同类告警，一次故障只发一条
2. `inhibit_rules`：根因告警抑制衍生告警
3. `silence`：计划维护期间临时静默
4. `group_wait` + `group_interval`：控制发送频率

### Q12：Ansible Playbook 幂等性

**面试官问法：**

> Ansible Playbook 中 role、task、handler 分别是什么？如何保证幂等性？

**核心概念：**

```
Role    → 可复用的 Playbook 单元（目录结构：tasks/handlers/templates/vars）
Task    → 具体执行步骤（使用模块）
Handler → 仅在被 notify 时执行一次（常用于重启服务）
```

**幂等性的正确做法：**

```yaml
# 正确：用模块的 state 声明，天然幂等
- name: 安装 nginx
  yum:
    name: nginx
    state: present          # 已安装则跳过

- name: 启动并开机自启
  service:
    name: nginx
    state: started
    enabled: yes

# 错误：直接用 shell 命令，每次都会执行
- name: 安装 nginx（错误写法）
  shell: yum install -y nginx    # 重复执行也会运行

# 如果必须用 shell，加 creates 条件
- name: 解压文件
  shell: tar -xzf app.tar.gz
  args:
    creates: /opt/app/bin/start.sh   # 文件存在则跳过
```

## 四、项目深挖

### Q13：Nginx + Keepalived 高可用 — 切换原理

**面试官问法：**

> 主备切换时间小于 3 秒是如何实现的？切换过程中已有的 TCP 长连接会怎样处理？

**VRRP 切换原理：**

```
正常状态：
  主节点每秒发送 VRRP 心跳广播
  从节点监听心跳

触发切换（默认 3 次心跳超时 = 3 秒）：
  从节点检测到 3 次未收到心跳
  → 从节点宣告自己成为 MASTER
  → 发送免费 ARP 广播，刷新网络设备的 ARP 缓存
  → VIP 漂移到从节点
  → 整个过程 < 3 秒
```

**已有 TCP 长连接的处理：**

- VIP 切换后，已建立的 TCP 连接会**中断**（四元组中服务端 IP 变了但实际处理机器变了）
- 客户端需要重建连接
- 应对方案：应用层连接池 + 自动重试（Spring Retry / Resilience4j），对业务无感知

### Q14：容器化改造 — 真实性验证

**面试官问法：**

> 部署时间从 2 小时压缩到 20 分钟，原来 2 小时都花在哪里？

**原流程（手动部署，逐步拆解）：**

```
1. 开发打包 jar（10min）
2. 通过堡垒机 scp 传输 jar 到各服务器（5min × N台）
3. 手动停止旧进程（kill + 确认）
4. 修改配置文件（每台机器都要改，容易出错）
5. 启动新进程（nohup java -jar ...）
6. 检查日志确认启动成功
7. 通知测试验证（等待回复）
全程：人工操作多，依赖人盯着，出错需手动回滚
```

**容器化后（20min）：**

```
Jenkins Pipeline 自动触发：
1. git pull + maven build（5min）
2. docker build + push 到 Harbor（5min，层缓存）
3. kubectl set image 触发滚动更新（5min，含健康检查）
4. 异常自动回滚（kubectl rollout undo）
全程：无人值守，一键发布
```

### Q15：Python 巡检脚本与 K8s API 交互

**面试官问法：**

> 巡检脚本是通过什么方式与 K8s API 交互的？

**推荐方式：kubernetes Python client**

```python
from kubernetes import client, config

# 集群内运行（Pod 内）
config.load_incluster_config()
# 集群外运行（本地调试）
# config.load_kube_config()

v1 = client.CoreV1Api()

def check_pods(namespace="default"):
    pods = v1.list_namespaced_pod(namespace)
    for pod in pods.items:
        name = pod.metadata.name
        phase = pod.status.phase
        # 检查非 Running 状态的 Pod
        if phase not in ["Running", "Succeeded"]:
            print(f"[WARN] Pod {name} is in {phase} state")
            # 可进一步获取事件、重启次数等
            restart_count = sum(
                c.restart_count
                for c in (pod.status.container_statuses or [])
            )
            print(f"  Restart count: {restart_count}")
```

**权限配置（RBAC）：**

```yaml
apiVersion: v1
kind: ServiceAccount
```

### Q16：SRE 岗位认知 — 面试官最看重这道题

**面试官问法：**

> SRE 的核心理念是什么？如果让你为核心接口制定 SLO，你会怎么设计？

**SRE 的本质：**

> SRE 是用软件工程方法解决运维问题。核心理念是：**用数据（SLO/Error Budget）来客观量化可靠性，用 Error Budget 来平衡稳定性和研发速度，而不是靠感觉或"谨慎为主"来运维。**

**制定 SLO 的完整步骤：**

```
1. 选 SLI：从用户视角选指标
   → 可用性（接口成功率）+ 延迟（P99 < 200ms）

2. 看历史数据：
   → 过去 3 个月 Prometheus 数据：实际可用率 99.94%，P99 = 180ms

3. 设定 SLO（略严于历史）：
   → 可用性 SLO：99.9%（28天滚动）
   → 延迟 SLO：95% 的请求 P99 < 200ms

4. 计算 Error Budget：
   → 28天 × 24h × 60min × 0.1% = 40.3 分钟/月

5. 配置告警：
   → 消耗速率 > 2x 时（即用 1 天用掉 2 天的预算），PagerDuty 告警

6. 定期复盘：
   → 每月末评估：SLO 是否被持续触碰？需要收紧还是放宽？
```

## 六、SRE 核心体系：SLI / SLO / SLA / Error Budget

> 此部分见单独笔记《SRE核心体系_SLI_SLO_SLA_ErrorBudget.md》，已合并关键内容如下。

### 概念速览

|概念|全称|一句话定义|负责人|
|---|---|---|---|
|**SLI**|Service Level Indicator|实测服务质量指标（客观数字）|SRE 团队|
|**SLO**|Service Level Objective|内部设定的 SLI 目标值|SRE + 产品|
|**SLA**|Service Level Agreement|对外的合同承诺，违约有赔偿|业务 + 法务|
|**Error Budget**|误差预算|`100% − SLO`，允许出错的配额|SRE + 研发|

### Error Budget 决策框架

```
预算消耗 < 50%    →  正常发布节奏，可进行混沌工程演练
预算消耗 50~75%  →  正常发布，关注近期趋势
预算消耗 75~100% →  降低发布频率，高风险变更需审批
预算消耗 ≥ 100%  →  冻结非关键发布，优先修复稳定性问题
```

### 典型 SLO 数值

|SLO|每月允许停机时长|适用场景|
|---|---|---|
|99%|~7.2 小时|内部工具|
|99.9%|~43.2 分钟|普通 To-B 服务|
|99.95%|~21.6 分钟|核心业务接口|
|99.99%|~4.3 分钟|支付、核心链路|

### 面试高频问答

**Q：SLI、SLO、SLA 有什么区别？**

> SLI 是实测指标，SLO 是内部目标，SLA 是对外合同。用 SLI 衡量质量，用 SLO 约束工程团队，用 SLA 向客户承诺。SLO 通常比 SLA 严格，为违约留出缓冲。

**Q：Error Budget 是什么，有什么用？**

> Error Budget = 1 − SLO，是允许出错的配额。核心价值是平衡稳定性和研发速度：预算充足时放心发布，预算告急时强制降速优先修复，用数据代替主观判断。

**Q：SLO 为什么比 SLA 严格？**

> SLO 触发内部复盘，SLA 触发赔偿。让 SLO 先一步触碰，团队能提前介入修复，避免最终违反 SLA 产生商业损失。这个缓冲层是风险管理的基本手段。
