每一个 Java 开发者都习惯了不需要手动 `free` 内存的便利，但这种便利是有代价的。当我们谈论 JVM 垃圾回收（Garbage Collection, GC）时，很多人脑子里跳出来的是“标记-清除”、“老年代”、“新生代”这些术语。

但在 2023 年这个时间点回看，随着 ZGC 和 Shenandoah 的成熟，GC 的底层哲学已经发生了剧变：我们不再仅仅追求吞吐量，而是在疯狂地压低**停顿时间（Pause Time）**。

今天这篇博客，我想从底层的对象生存假说聊起，深入剖析 GC 的物理演进，并拆解现代 GC 最硬核的黑科技——染色指针（Colored Pointers）。

## 1. 根搜索算法：谁才是真正的“活”着？

在垃圾回收之前，JVM 必须解决第一个哲学问题：哪些对象已经死了？

### 引用计数法的局限
早期的思路是引用计数（Reference Counting）：给对象加个计数器。但它无法处理**循环引用**（A 引用 B，B 引用 A，但两者都与外界断开）。

### 根搜索算法 (Reachability Analysis)
现代 JVM 使用根搜索。底层原理是：从一组 **GC Roots** 出发，沿着引用链向下搜索，能搜到的就是活的。
**GC Roots 包括哪些？**
- 栈帧中的局部变量表。
- 方法区中的静态属性同步引用。
- 本地方法栈（JNI）中的引用。

**深度思考**：寻找 GC Roots 的过程需要一个瞬间的“一致性快照”，这就是为什么哪怕是最先进的 GC 也无法完全避免 Stop-the-World (STW)。

## 2. 分代收集假说：垃圾回收的“厚黑学”

JVM 的回收策略建立在两个核心假说之上：
1. **绝大多数对象都是朝生夕死的。**
2. **熬过越多次回收的对象，越难死掉。**

基于此，堆内存被划分为 **新生代 (Young Gen)** 和 **老年代 (Old Gen)**。
- 新生代使用 **标记-复制算法**：内存被分为 Eden 和两个 Survivor 区。因为大部分对象都会死，所以只需拷贝少量活对象。
- 老年代使用 **标记-整理算法**：因为对象存活率高，拷贝开销太大，所以选择将活对象推向内存的一端，清理掉边界外的空间。

## 3. 从 CMS 到 G1：分而治之的进化

早期的 Parallel 回收器是“全量回收”，当堆内存达到 32GB 甚至更高时，扫描全堆的时间会让应用停顿到无法忍受。

**G1 (Garbage First)** 的出现改变了游戏规则。它不再坚持物理上的连续分代，而是将堆拆成几千个独立的 **Region**。
底层原理是：**价值优先**。G1 会跟踪每个 Region 里的“回收价值”（即回收能释放的空间与耗时的比例），每次只回收最有价值的那部分 Region。这让停顿时间变得“可预期”。

## 4. ZGC：真正意义上的革命

到了 Java 11/17，ZGC（Z Garbage Collector）将停顿时间压低到了 **1ms 以下**，且不受堆大小影响。这背后的原理极其迷人。

### 核心黑科技 1：染色指针 (Colored Pointers)
以前我们把对象的垃圾回收状态（如是否标记过、是否移动了位置）存在对象头（Object Header）里。
ZGC 做了一个极其大胆的设计：**利用 64 位指针中多出来的位来存状态。**
在 64 位系统中，由于物理内存上限，我们通常只用到 42-48 位。ZGC 拿出了 4 位来表示：
- **Marked0/Marked1**: 标记位。
- **Remapped**: 指针是否指向了对象的新地址。
- **Finalizable**: 是否只能通过 finalizer 访问。

**底层精髓**：这意味着通过读取指针本身（寄存器级别），JVM 就能知道对象的回收状态，而不需要先从内存里把对象读取出来查看对象头。

### 核心黑科技 2：读屏障 (Load Barriers)
由于 ZGC 允许在回收的同时应用线程继续运行（并发重定位），如果应用线程去读一个正在移动的对象怎么办？
底层原理是：**当应用线程读取一个对象引用时，会触发一个轻量级的拦截逻辑（Load Barrier）**。它会检查指针的染色位。如果是错的（旧地址），拦截器会自动根据转发表（Forwarding Table）把指针修正为新地址并写回。
这就是所谓的 **“Self-healing（自愈）”**。

## 5. 权衡：没有免费的午餐

ZGC 实现了极低的停顿，但它是以 **吞吐量 (Throughput)** 为代价的。
因为：
1. **读屏障的开销**：每次读对象引用都要多执行几行指令，这累积下来会损耗 5%~15% 的性能。
2. **内存空间的妥协**：染色指针目前无法利用压缩指针（Compressed OOPs），导致堆内存利用率略低于 G1。

**选型策略**：如果你的应用响应时间极其敏感（如交易系统、交互式搜索），选 ZGC；如果你的应用是离线批处理（如离线数据分析），G1 或 Parallel 可能更合适。

## 6. 总结

Java 垃圾回收的历史，本质上是人类与 **“内存碎片”** 和 **“停顿延迟”** 斗争的历史。

从最初粗犷的 Stop-the-World，到 G1 的分而治之，再到 ZGC 利用 64 位地址空间的“神来之笔”，我们可以看到 JVM 工程师们在物理极限内持续掘进的智慧。

理解这些原理，不仅仅是为了应对面试中关于“G1 和 ZGC 区别”的问题，更是为了当你在生产环境中面对 JVM 停顿导致的接口超时时，能透彻地明白那短暂的几百毫秒里，底层究竟发生了怎样的微观博弈。
