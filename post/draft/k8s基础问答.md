## 1. Pod 的生命周期 (Pod Lifecycle)

面试官通常会问：“一个 Pod 从创建到销毁经历了哪些阶段？”

### 核心阶段 (Phase)

1. **Pending**：API Server 已经创建了 Pod 资源，但还没被调度到节点上，或者正在拉取镜像（你之前遇到的网络问题就常停在这里）。
    
2. **Running**：Pod 已绑定到节点，且容器已创建，至少有一个容器正在运行或重启。
    
3. **Succeeded**：所有容器成功运行并退出（常见于 Job/CronJob）。
    
4. **Failed**：容器以非 0 状态退出。
    
5. **Unknown**：通常是由于 Master 无法与该 Pod 所在的 Node 通信。
    

### 高级加分项：状态背后的状态

- **Init Containers**：在主容器启动前运行。如果 Init 容器失败，Pod 会不断重启直到成功。
    
- **Readiness (就绪探针)**：决定 Pod 是否接收流量。如果失败，Pod 还在 Running，但 Service 会把它从转发列表中踢出。
    
- **Liveness (存活探针)**：决定是否重启容器。

## 2. Service 的三种主要模式

面试官会问：“你的微服务如何被访问？这三种模式有什么区别？”

### ① ClusterIP (默认)

- **场景**：**内部通信**（如你的 MongoDB/Redis）。
    
- **原理**：分配一个仅集群内部可达的虚拟 IP。
    
- **关键点**：它解决了 Pod IP 经常变动的问题，提供了一个稳定的 DNS 访问入口。
    

### ② NodePort

- **场景**：**开发/调试**或小型集群外部接入（如你简历中访问 RabbitMQ 管理页面）。
    
- **原理**：在每个 Node 上开一个固定端口（默认 **30000-32767**），通过 `NodeIP:NodePort` 访问。
    
- **面试坑点**：缺点是端口管理麻烦，且不适合大规模生产环境。
    

### ③ LoadBalancer

- **场景**：**公网发布**（云厂商环境，如阿里云、AWS）。
    
- **原理**：K8s 会调用云平台的 API 自动创建一个外部负载均衡器。
    
- **关键点**：这是企业级最常用的接入方式，能自动处理流量分发和扩容。

## 3. Controller Manager 的工作原理

这是考察你对 K8s **“声明式 API”** 理解最深的一环。

### 核心逻辑：控制循环 (Control Loop)

Controller Manager 就像一个**永不停歇的巡检员**，它只做三件事：

1. **观察 (Observe)**：通过 List-Watch 机制监控集群资源的当前状态（Actual State）。
    
2. **分析 (Analyze)**：对比“当前状态”与用户定义的“期望状态”（Desired State，即你写的 YAML）。
    
3. **行动 (Act)**：如果两者不一致，就执行操作（如创建、删除 Pod）让现状趋向期望。
    

### 典型例子：Deployment Controller

- 如果你把 `replicas` 从 3 改成 5。
    
- Controller 发现少了 2 个，就会调用 API Server 请求创建 2 个新 Pod。
    
- 如果一个节点挂了，上面的 Pod 没了，Controller 发现现状（0）< 期望（1），就会在其他节点重新拉起。

### 1. 关于滚动更新 (Rolling Update)

**Q：`maxSurge` 和 `maxUnavailable` 如何设置？**

- **回答思路：** 这取决于业务对“可用性”和“资源冗余”的权衡。
    
    - **`maxSurge` (最大增量)**：定义了在更新过程中可以比预期副本数多出多少个 Pod。通常设为 **25%**。如果是为了追求极致的平滑（防止老 Pod 还没下线，新流量由于容量不足被压垮），可以设高一点（如 50%）。
        
    - **`maxUnavailable` (最大不可用数)**：定义了在更新过程中最多有多少个 Pod 处于不可用状态。在生产环境中，为了保证高可用，通常设为 **0**（即：先启动新 Pod，确认就绪后再删老 Pod）。
        
- **Q：新版本 `CrashLoopBackOff` 时，流量如何处理？**
    
    - **回答思路：** 这是 K8s 的保护机制。
        
    
    1. **流量隔离**：由于 Pod 崩溃，其 `Readiness Probe`（就绪探针）必然失败。Service 会自动将该 Pod 从 Endpoints 列表中移除，流量**不会**流向崩溃的新 Pod，而是继续由存活的老版本 Pod 处理。
        
    2. **暂停更新**：滚动更新会停滞。因为新 Pod 无法就绪，无法满足“达到预期副本数”的条件，K8s 不会继续删除剩余的老 Pod，从而保障了业务不中断。

### 2. 关于 CI/CD 与版本管理

**Q：镜像版本号（Tag）策略是什么？**

- **回答思路：** 严禁在生产环境使用 `latest` 标签。我通常采用 **“Git Commit ID + Build ID”** 或 **“语义化版本 (v1.2.3)”** 的组合。
    
    - 在 Jenkins 流水线中，我会通过 Shell 脚本获取当前的 `GIT_COMMIT` 前七位，构建出类似 `myapp:20241027-a1b2c3d` 的镜像。这样可以实现代码提交与镜像版本的一一对应。
        

**Q：一键回滚的底层原理？**

- **回答思路：**
    
    - 如果是使用 Helm 管理的应用，底层原理是 **`helm rollback`**。它更强大，因为 Helm 会记录整个 Release 的历史（包括 ConfigMap、Secret 等所有关联资源的状态），不仅回滚镜像，还回滚配置。
        
    - 如果只用了纯 YAML，底层则是 **`kubectl rollout undo`**。它通过 API Server 查找 Deployment 关联的 `ReplicaSet` 历史版本，将模板重新切回旧的 ReplicaSet。

### 3. 关于 Ingress 与外部接入

**Q：Ingress 和 Service (NodePort) 的本质区别？**

- **回答思路：**
    
    - **层级不同**：NodePort 工作在 **L4（传输层）**，只负责端口转发；Ingress 工作在 **L7（应用层）**，可以基于域名、URL 路径进行流量分发。
        
    - **效率与成本**：NodePort 需要在每个节点开端口，管理混乱；Ingress 只需要一个统一的入口（如 Nginx Ingress Controller），通过反向代理管理成百上千个微服务，支持 SSL 卸载。
        

**Q：单节点环境如何解决外部流量接入？**

- **回答思路：** 在 Minikube 或单机环境，我通常使用 **`minikube tunnel`**（它会模拟一个负载均衡器 IP）或者直接将 Ingress Controller 的服务类型设为 **`NodePort`**，然后通过 Windows 的 `hosts` 文件将域名指向 WSL 的 IP。
    

---

### 4. 深度追问：多节点跨主机通信 (CNI)

**Q：Pod 跨主机通信原理（Calico/Flannel）？**

- **回答思路：** 核心是解决 **“Pod IP 全局唯一且可路由”** 的问题。
    
    - **Flannel (VXLAN 模式)**：这是最常见的方案。它采用 **Overlay（叠加网络）** 技术，将原始的 Pod 数据包封在一个 UDP 包里（类似隧道），通过物理机网络传输到目标节点后再解包。
        
    - **Calico (BGP 模式)**：这是更高性能的方案。它不进行封包，而是把每个 Node 都看作一台路由器，通过 BGP 协议在节点间同步路由表。Pod 之间的流量直接通过物理网络路由，几乎没有性能损耗。
        
- **总结**：Flannel 简单、兼容性好；Calico 功能强大（支持网络策略/防火墙），性能更高。

### 1. 关于标准化巡检与 `iowait` 排查

**Q：脚本检查哪些指标？**

- **基础指标**：CPU（Load Avg, Idle）、内存（Used, Free, Buffer/Cache）、磁盘（Usage, Inodes）、网络（带宽占用, TCP 连接状态）。
    
- **服务状态**：关键进程是否存在（`ps`）、监听端口是否存活（`netstat/ss`）。
    
- **日志异常**：`/var/log/messages` 或 `dmesg` 中的硬件错误、内核 OOM 关键词。
    

**Q：`iowait` 持续过高排查思路？**

- **定义核心**：首先明确 `iowait` 是 CPU 在等待磁盘 I/O 完成的空闲时间，说明瓶颈在 IO。
    
- **定位进程**：使用 **`iotop`** 实时查看哪个进程在疯狂进行读写。
    
- **分析读写详情**：使用 **`iostat -x 1 5`** 查看磁盘的具体表现。观察 `%util`（磁盘忙碌程度）和 `await`（平均响应时间）。如果 `await` 远大于服务正常值，说明磁盘物理性能达到上限。
    
- **深度排查**：
    
    - 如果是数据库：检查是否有大表的慢查询全表扫描。
        
    - 如果是日志：检查是否有 debug 日志未关闭导致频繁刷盘。
        
    - 如果是系统：检查是否触发了 `swap`（虚拟内存）交换，导致大量的随机 IO。

### 2. 关于 Docker 改造的“坑”与日志/网络

**Q：遇到过最大的坑？**

- **回答示例**：**“僵尸进程与信号传递”**。在容器化初期，如果没配置好 `init` 进程（如 Tini），容器内的 1 号进程无法回收子进程，导致大量僵尸进程。或者在 `docker stop` 时，程序收不到 `SIGTERM` 信号，导致无法优雅停止，数据库连接被直接强切导致数据受损。
    

**Q：日志持久化处理？**

- **日志驱动**：在 Docker Compose 中配置 `json-file` 驱动，并设置 `max-size` 和 `max-file`，防止单个日志文件撑爆磁盘。
    
- **挂载策略**：使用 **Volume 挂载**。将容器内的 `/app/logs` 映射到宿主机的特定目录，结合你简历里的 **ELK**（使用 Filebeat 扫描宿主机挂载目录）实现日志采集，确保容器销毁后日志不丢失。
    

**Q：容器间网络通信？**

- **内置 DNS**：Docker Compose 会自动创建一个默认网络。我利用服务的 **Service Name** 直接通信（如 Web 连接 `db:3306`），而不是写死 IP，这保证了环境迁移时的一致性。

### 3. 关于 Prometheus 告警风暴与 CPU 飙升

**Q：如何处理“告警风暴”？**

- **分组（Grouping）**：在 Alertmanager 中配置分组，比如 10 台机器同时宕机，只发一条包含 10 个信息的告警，而不是 10 条短信。
    
- **抑制（Inhibition）**：配置依赖关系。如果数据中心网络断了，就抑制该机房内所有服务器的心跳告警，只发“网络断开”的主告警。
    
- **静默（Silencing）**：在计划内维护时，提前配置静默窗口，避免无效干扰。
    

**Q：CPU 飙升但日志无异常，如何深度定位？**

- **回答思路**：说明这是典型的“暗箱故障”，需要动用底层工具。
    
- **三板斧**：
    
    1. **`top` 然后按 `P`**：定位占用 CPU 最高的进程。按 `H` 查看是哪个线程（TID）在忙。
        
    2. **`perf top`**：这是大招。它能实时显示内核函数和用户态函数调用分布，直接看出是哪个函数在消耗 CPU（比如加密解密、频繁的 GC、或者某些系统调用）。
        
    3. **`strace -p <pid> -c`**：统计该进程系统调用的时间分布，看看是否因为频繁的磁盘读写或网络等待导致了系统调用开销过大。

### 1. 关于 Keepalived 的故障转移机制

**Q：Nginx 进程挂了，VIP 会自动漂移吗？**

- **标准答案**：**默认不会**。Keepalived 协议（VRRP）主要监控的是“机器存活”。只要服务器网络协议栈还在响应 VRRP 报文，VIP 就会停留在该机器上，即便 Nginx 已经无法提供服务。这会导致前端流量进入该机器后直接报错（502/连接拒绝）。
    

**Q：你是如何通过脚本解决的？**

- **回答思路**：通过在 `keepalived.conf` 中配置 `vrrp_script`。
    
    1. **编写脚本**：写一个简单的 Shell 脚本，使用 `killall -0 nginx` 或 `curl` 本地 80 端口来判断 Nginx 存活。
        
    2. **权重调整**：在脚本中，如果探测失败，则返回非 0 状态码。Keepalived 接收到失败信号后，会根据配置调低当前节点的 `priority`（优先级）。
        
    3. **触发漂移**：当主节点优先级低于备节点时，VIP 就会发生漂移，实现应用层的高可用。

### 2. 关于数据库高可用（MHA）与数据一致性

**Q：MHA 如何保证数据一致性？**

- **核心点**：通过 **`save_binary_logs`** 机制。
    
    1. 当主库（Master）挂掉但其 SSH 仍可访问时，MHA 会立即远程登录主库，尝试保存还未发送到从库（Slave）的二进制日志（Binary Logs）。
        
    2. 然后将这些差异日志应用到选出的新主库上。
        

**Q：从库之间的数据差异如何补偿？**

- **核心点**：利用 **`apply_diff_relay_logs`** 过程。
    
    1. 由于不同从库同步主库的速度（IO Thread）可能不同，它们各自的 Relay Log 进度也不同。
        
    2. MHA 会对比所有从库的 Relay Log，找出“最快”的那台，并计算出其他从库落后的部分。
        
    3. 生成差异補丁并在其他从库上执行，确保所有从库在切换前都对齐到同一个逻辑时间点，从而保证数据一致。

### 3. 关于内核调优：TCP 队列与 Swap

**Q：调优 TCP 队列具体指哪个参数？**

- **回答思路**：高并发场景下，**两个都要调**，但它们对应的阶段不同。
    
    - **`net.ipv4.tcp_max_syn_backlog`**：这是 **半连接队列 (SYN Queue)**。用于存放收到客户端 SYN 包但还没完成三次握手的请求。如果该值过小，在高并发 SYN Flood 或连接瞬间爆发时，会导致客户端连接超时。
        
    - **`net.core.somaxconn`**：这是 **全连接队列 (Accept Queue)**。用于存放已完成三次握手、等待应用程序（如 Nginx）`accept` 的请求。如果 Nginx 处理不过来，这个队列满了，内核会直接给客户端发 RST 包或丢弃请求。
        

**Q：为什么要调整 `vm.swappiness`？**

- **核心点**：**减少不必要的磁盘 IO 抖动**。
    
    - `swappiness`（范围 0-100）决定了内核在内存不足时，多大程度上倾向于把内存数据交换到 Swap 分区。
        
    - **原因**：在运行数据库（如 MySQL、MongoDB）或区块链节点时，数据读写对 IO 极其敏感。如果内核将这些活跃程序的内存页交换到磁盘，会导致严重的性能掉速。
        
    - **做法**：通常设为 **10**（甚至在特定场景下设为 **0** 或 **1**），强制内核优先回收 File Cache（缓存的文件内容），不到万不得已不去动进程的物理内存。
